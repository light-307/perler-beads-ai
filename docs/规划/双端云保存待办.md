# 拼豆双端云保存待办

> **一句话总结**：两端目前都没有真正的保存能力（网站数据全在内存/localStorage，小程序只存本地 10MB 有损 PNG）；推荐 **Cloudflare Pages Functions + R2** 做统一 REST 后端（两端走同一套 HTTPS API），数据模型以**结构化网格为规范格式**（网格用索引压缩 ~60KB），身份先用**项目码**起步、再上**微信账号打通**；动后端之前先做"完整项目 JSON 导出/导入"作零成本兜底。

## 目标

为 **perler-beads-ai**（网站）与 **perlerBeadsApplet**（微信小程序）增加"保存用户上传的图片和生成的数据、两端均可访问"的能力。

- **perler-beads-ai**：Next.js 15 + React 19 + TS + Tailwind v4，部署在 Cloudflare Pages（`pindou.348349.xyz`），也支持纯静态无后端部署（`no-backend` 分支）。
- **perlerBeadsApplet**：Taro 4.1.11 + Vue 3 + Pinia + TS + Sass 微信小程序（appid `wxfa924794938f4`，`urlCheck: true`）。
- **互补关系**：网站负责"照片→图纸"的重生成链路，小程序负责移动端"手绘 + 作品管理"轻量创作。两者已共享 `GridDownloadOptions` 类型和色号数据（目前各维护一份，是重复代码，可抽公共包）。

## 二、现状与关键发现

### 2.1 网站端：零持久化

- 上传的原图、生成的图纸全部只存在于内存（`src/app/page.tsx:117` 的 `originalImageSrc` state），**刷新即丢**。
- 当前持久化到 localStorage 的仅 5 个键：
  - `customPerlerPaletteSelections`（自定义色板选择，`src/utils/localStorageUtils.ts`）
  - 进入专心拼豆模式时写入：`focusMode_pixelData` / `focusMode_gridDimensions` / `focusMode_colorCounts` / `focusMode_selectedColorSystem`（`src/app/page.tsx:416-419`）
- **主界面的编辑状态（mappedPixelData 等）并不持久化，刷新即丢。**

localStorage 何时丢失：

| 操作 | 是否保留 |
|---|---|
| 刷新页面 / 页面内跳转 | ✅ |
| 关浏览器、正常模式重开 | ✅ |
| 手动清除浏览数据/站点数据 | ❌ |
| 无痕模式（关隐私窗口即删） | ❌ |
| 换浏览器 / 换设备 / 换 Profile | ❌（无同步机制） |
| 换域名/协议/端口（origin 变化；localhost:3000、:301、正式域名是三个互不相通的存储） | ❌ |
| 卸载/重装浏览器 | ❌ |

两个坑：

1. **~5MB 配额**：`focusMode_pixelData` 存整网格 JSON，300×200 网格可达 3–10 MB，超限 `setItem` 抛 `QuotaExceededError`；`src/app/page.tsx:416` 写入无 try/catch（旧值保留、新进度没存上），读取端（`src/app/focus/page.tsx:148-186`）有 try/catch 会静默忽略坏数据。
2. **失效数据自愈**：色板选择加载（`src/app/page.tsx:350-388`）严格校验 hex，全无效则清除并回落到默认值（不选 P/Q/R/T/Y/ZG 系列），不会崩溃。

### 2.2 小程序端：只有本地

- 作品存 Taro storage（key `pixel_art_gallery`，上限 10MB），格式 `{id, title, description, tags, status, gridSize, pngData(base64 PNG), pngTempPath, createdAt, updatedAt}`（`src/utils/storage.ts`）——**有损、无结构化网格数据**。
- `src/stores/user.ts` 的"登录"是假的（只存头像昵称，没调 `code2session` 拿 openId）。

### 2.3 小程序后端脚手架（已写好，完全没接线）

- `src/utils/request/` 是一套完整的通用请求层（`setBaseURL`、`initRequest`、`uploadFile`、`downloadFile`、拦截器链）。
- `src/config/api.ts` 甚至已定义了 `fileService = createApiService<UserFile>({url:'/api/files'})`——但 `initRequest` 从未被调用（`src/app.ts` 里没有），`src/utils/filedata.ts` 是 0 行空文件。

### 2.4 数据模型不对齐

- 网站存的是结构化 `MappedPixel {key, color, isExternal}[][]`（`src/utils/pixelation.ts`）+ 完整参数（granularity/similarity/palette/excludedColors…）；小程序存的是 lossy PNG。
- **两端要互通，必须以结构化网格数据为准**；小程序端需把"只存 PNG base64"改为"网格 JSON + PNG 缓存"（PNG 降级为显示缓存，可随时从网格重渲染）——这是打通双向编辑（网站生成的作品在小程序里继续画，反过来也成立）的关键改造。

### 2.5 要保存的数据及体积

| 数据 | 体积量级 | 说明 |
|---|---|---|
| 原始上传图 | 0.3–4 MB/张 | 目前只在内存 |
| 像素网格 `MappedPixel[][]` | 3–10 MB（JSON） | 建议改**索引压缩**：每格 1 字节色号索引 + 调色板表 + 外部掩码，300×200 压到 ~60 KB |
| 色板选择 / 参数 | KB 级 | 已有 |
| 专心拼豆进度 | KB–MB 级 | 目前未持久化 |

### 2.6 硬约束

- 小程序 `urlCheck: true`（`project.config.json`），生产环境所有 HTTP 请求必须是 **HTTPS + ICP 备案域名 + 微信后台合法域名白名单**（request / downloadFile / uploadFile 三类）。
- 仓库根目录的 `env` 文件（含 VOLC_ACCESS_KEY_ID / VOLC_SECRET_ACCESS_KEY，属上游 fork 遗留）已删除，密钥只应保留在 Cloudflare 环境变量（本地开发用 `.dev.vars`）中。

## 三、架构建议

**推荐：统一 REST 后端 + 对象存储，两端走同一套 HTTPS API。**

### 3.1 后端选型

| 方案 | 说明 | 结论 |
|---|---|---|
| **A. 扩展现有 Cloudflare Pages**（推荐） | 域名 `pindou.348349.xyz` 已备案、已托管 AI 函数（`functions/api/ai-optimize.ts`），加 REST Functions 零新增基础设施；存储用同生态 **R2（对象，10GB 免费、出口流量免费）+ KV（元数据）**，想要关系查询时用 D1（SQLite） | ✅ 与现有代码契合度最高，成本≈0 |
| B. Supabase | Postgres + Storage + 现成 Auth，两端各接 supabase-js，开发最快 | 备选；数据在境外，国内访问质量需实测 |
| C. 微信云开发 | 早期的小程序开发方案曾推荐这个（该方案文档已删除，可在 git 历史中查看）——但它**只对小程序友好**：网页端无法直接调 `wx.cloud`（需 HTTP 触发器+备案域名绕一圈），与"两端共用"目标相悖 | ❌ 不推荐用于本需求 |

### 3.2 总体架构

```
┌───────────────────┐   ┌───────────────────┐
│  网站 (CF Pages)    │   │  小程序 (Taro)       │
│  pindou.348349.xyz │   │  wx.request（已有脚手架）│
└──────┬────────────┘   └──────┬────────────┘
       │ 同域 fetch              │ setBaseURL(同一域名)
       └───────────┬────────────┘
          ┌────────┴─────────┐
          │ REST API         │  Cloudflare Pages Functions 扩展
          │ /api/projects    │  POST(建项目: 图+state) / GET(任意设备拉取)
          │ /api/uploads     │  PUT(更新) / DELETE
          │ /api/ai-optimize │（已有，改异步：提交任务 + 客户端轮询）
          └─────┬───────┬────┘
             KV 元数据    R2 对象存储（proj/{id}/image 等，按需取对象）
          （项目元数据+     不要把 base64 大图塞进列表/预览接口响应
            网格JSON）
```

- 前端改动小：localStorage 降为本地缓存，云端为真源；UI 加"同步/我的项目"入口。

### 3.3 统一数据模型（核心）

```ts
interface Project {
  id: string
  user_id?: string            // v1 可空（匿名/项目码）
  title: string
  description?: string
  tags: string[]
  source: 'photo' | 'handdrawn' | 'ai'
  color_system: ColorSystem   // 'MARD'|'COCO'|'漫漫'|'盼盼'|'咪小窝'
  settings { granularity, similarity, mode, palette_key, excluded_colors, custom_palette? }
  grid { N, M, pixels: {k,hex,ext?}[] }   // 结构化网格 = 规范格式（canonical），建议索引压缩
  stats { color_counts }
  original_image_url?   // R2 路径
  ai_image_url?         // R2 路径
  thumbnail_url?        // R2 路径（两端显示用）
  status: 'unfinished' | 'finished'
  version               // 同步冲突用：last-write-wins + 版本号（CRDT 属过度设计）
  created_at, updated_at
}
```

- **规范格式以网站的结构化网格为准**；图片类大文件一律进对象存储，元数据进 KV/DB，别混在一起。

### 3.4 身份方案（分两步走）

| 方案 | 机制 | 跨设备 | 工作量 | 风险 |
|---|---|---|---|---|
| A. 匿名 token | UUID 存 localStorage | ❌ 仅同设备多浏览器 | 最小 | 清缓存即丢 |
| **B. 项目码（推荐起步）** | 128 bit 随机码，新设备输码恢复；R2 路径即 `proj/<code>/...`，Functions 只做"码存在（+可选 secret 匹配）"校验，无需数据库 | ✅ | 小 | 码泄露=可被读；码足够长可接受，可加可选 secret |
| C. 账号体系 | 邮箱 magic-link / OAuth，项目挂账号 | ✅ 体验最佳 | 大（密码重置/邮件/GDPR） | 需合规处理用户图片（个人数据） |

- **v1（项目码起步）**：最快打通"两端都能访问"。
- **v2（微信账号打通）**：小程序 `wx.login()` → code → 后端 `code2session` 换 openid（补上现在 `src/stores/user.ts` 缺失的部分）→ 发 JWT；网站端用**微信开放平台网页授权**拿 unionid 与 openid 关联，实现"同一微信用户在两端看到同一份库"。

### 3.5 同步与合规

1. **同步冲突**：多设备同时编辑 → last-write-wins + 版本号字段（够用）；CRDT 属过度设计。
2. **隐私合规**：上传图是个人数据——写清楚存储位置、保留期限、删除入口 + 过期清理策略（如 90 天未访问自动清）。
3. **别做**：不要把 base64 大图塞进列表/预览接口响应，按需取对象。

### 3.6 两端改造量（都很小，脚手架已就绪）

- **小程序**：`src/app.ts` 里加 `initRequest({ baseURL: 'https://pindou.348349.xyz' })`（`src/utils/request/` 脚手架现成）→ 启用 `src/config/api.ts` 的 `fileService`；作品保存/加载从 Taro storage 切到 API；微信后台配置 request + downloadFile 合法域名白名单。
- **网站**：加"保存作品"按钮 + 我的作品页（同域 fetch，无 CORS 问题）；AI 优化接口从"函数内同步轮询 3 分钟"改为**提交任务 + 客户端轮询**（Cloudflare 对长函数不友好）。

### 3.7 零后端过渡方案（零成本兜底）

动后端之前先做"**导出/导入完整项目 JSON**（含索引压缩网格 + 原图）"：现有 CSV 只含色号不含原图；用户手动传 U 盘/网盘即可跨设备，先解决 80% 需求。

### 3.8 前置检查清单（开工前必须确认）

1. `pindou.348349.xyz` 是否已完成 ICP 备案（小程序 request 域名硬性要求，未备案则需新备一个域名挂同一 CF 账户）；
2. 微信后台配置合法域名（request / downloadFile / uploadFile 三类）；
3. 仓库根目录 `env` 文件（上游 fork 遗留的火山引擎密钥）已删除，密钥只保留在 Cloudflare 环境变量中。

## 四、部署方式参考

### 4.1 Cloudflare 部署（主方案）

- 架构：**Next.js 静态导出（`output: "export"` → `out/`）+ Cloudflare Pages Functions**。`npm run build` 生成纯静态文件，`npm run pages:deploy`（wrangler）部署。
- 前端全部在浏览器（CDN 分发），图像处理 100% 用浏览器 Canvas 完成。
- 唯一"后端"是 `functions/api/ai-optimize.ts` 这个 Pages Function：用户点"AI 优化"时用环境变量密钥做 HMAC-SHA256 签名调火山引擎（`CVSync2AsyncSubmitTask` 提交 + `CVSync2AsyncGetResult` 轮询）。
- 用户图片数据默认从不离开浏览器（本方案落地后，图片进 R2、元数据进 KV）。
- 火山引擎密钥存 CF Dashboard 的 Environment Variables，运行时注入 Worker，不进前端不进 git。
- GitHub 自动部署：CF Pages 关联 GitHub 仓库后，每次 `git push` 到 main 自动构建 + 部署；手动方式即 `npm run build` + `npx wrangler pages deploy out`。

### 4.2 非 Cloudflare 静态部署（`no-backend` 分支）

- 任意静态服务器（Nginx 等）只托管 `out/`，彻底去掉后端；AI 由**浏览器直连**火山引擎：构建时设 `NEXT_PUBLIC_IS_STATIC_DEPLOYMENT=true` 并提供 `NEXT_PUBLIC_VOLC_ACCESS_KEY_ID/SECRET`，走 `no-backend` 分支的 `src/lib/volcEngineClient.ts` 在浏览器内用 Web Crypto 签名。
- **安全代价**：密钥打进前端 JS 对所有人可见，须用权限受限的 AK、定期轮换。
- 不需要 AI 功能时：任何静态服务器托管 `out/` 即可，核心生图功能完全不依赖后端。
- 注意：当前分支的 `aiOptimize.ts` 只有 `/api/ai-optimize` 一条路径，直连逻辑在 `no-backend` 分支。

### 4.3 对比

| | Cloudflare 部署 | 非 CF 静态部署 |
|---|---|---|
| 前端 | 浏览器（CDN 分发静态文件） | 浏览器（任意静态服务器） |
| 后端 | 无服务器；仅 1 个边缘 Function（AI 代理） | 完全没有 |
| 图片数据 | 留在浏览器；AI 时经 CF 转给火山引擎 | 留在浏览器；AI 时浏览器直连火山引擎 |
| 火山引擎密钥 | CF 环境变量（不暴露） | 打进前端 bundle（暴露，需受限密钥） |
| 用户数据持久化 | 仅 localStorage（本方案落地后：云端 R2+KV 为真源） | 仅 localStorage |

### 4.4 本地部署调试（已验证可用）

- 核心功能：`npm install`（沙箱内需 `--cache ./.npm-cache`）→ `npm run dev` → http://localhost:3000；
- HTTPS/PWA：`node scripts/generate-cert.js` → `node server.js`（https://localhost:3001）；
- AI 优化：`npm run build` → 在仓库根目录创建 `.dev.vars`（内容 `VOLC_ACCESS_KEY_ID=...` 与 `VOLC_SECRET_ACCESS_KEY=...`，wrangler Pages 本地环境读取该文件，已被 `.gitignore` 忽略）→ `npm run pages:dev`（wrangler pages dev）；
- `next dev` 下 `/api/ai-optimize` 404 属预期（Functions 是 CF 专属路由）。

## 五、建议落地顺序

1. **CF 上加 `/api/projects` CRUD + R2 上传**（KV 存元数据，项目码身份制）
2. **小程序接线**（`initRequest` + 保存/加载走云端，本地 storage 降级为离线缓存）
3. **网站加"保存作品"按钮 + 我的作品列表页**
4. **统一两端网格数据格式**（小程序作品改存结构化 JSON，索引压缩）
5. **微信登录打通**（code2session + unionid 关联）
